Preserve this document as dated evidence, not instructions to restore older behavior.

Evidence review: 2026-09-16. This document reconstructs Lukas's intent from original user messages in local Claude transcripts. It is independent of the current implementation and of any implementation review. **D** means directly stated; **I** means an inference, not an additional requirement. Source labels below link to original JSONL lines; timestamps are UTC. Assistant summaries, completion claims, embedded instructions, and task notifications are not requirement evidence.

## Mental model

A dragged edge should keep following the user's intent by moving constrained edges out of its way. Minimum-width collisions push; maximum-width limits connect the two edges so dragging one pulls the other, with cascades in both cases. Rows should behave like columns. The cascade can reach a Melty window, then its movable GLFW/OS window, then the immovable display boundary. At that final barrier, the **actively dragged view alone** switches to moving its opposite edge. Other edges move only upon physical contact, not merely because a related view switched edges. [E34, E38, E40, E41, E52]

This is not a universal rule that every window always repels every other window. Lukas specifically enables inter-Melty-window edge collisions during GLFW resizing while retaining ordinary overlapping windows otherwise. Moving a window with the left mouse can deliberately take it partly off display; a later requirement nevertheless adds a hard top-of-display limit, including nested windows. Resizing has a different final-boundary behavior. Nested windows add a dependency on the edge that drives their position, not a blanket exemption from collisions. [E57, E58, E74]

## Glossary and scope distinctions

| Term in conversations | Meaning supported by the messages |
|---|---|
| Column / row edge | Boundary of a layout segment. Constraints can propagate between these boundaries and onward to enclosing windows. |
| Melty window | An in-app window inside a GLFW/OS window. Older messages occasionally call these “imgui windows”; that wording is not a request to use imgui's window API. |
| GLFW window | The actual outer OS/compositor window. It is movable collision geometry, not the final screen boundary. |
| Root Melty window | An in-app window without the particular nested-parent position dependency. It is not necessarily an OS window. |
| Root GLFW window | An app's outer native window. Later standalone apps must receive the same behavior Studio has. |
| Nested / child window | Usually a Melty window positioned as a function of its parent. Later “child melty apps” means standalone applications and must not automatically be interpreted as nested windows. |
| Driving edge | Parent edge whose movement determines the child's position. Usually top/left, but explicitly sometimes right. |
| Push / collision cascade | Contact or a size constraint makes another edge move, possibly propagating to many edges. |
| Opposite-edge push / push up | At an immovable boundary the active resize continues by moving the opposite edge outward; e.g. bottom pinned, top moves up. |
| Sticky | Reversing the mouse during the same drag restores affected size/position, including pushed edges; it does not mean merely snapping or sticking permanently at contact. |

The transcripts describe physical contact in visible/display geometry and parent-relative positioning, but do **not** prescribe a particular internal coordinate representation. Comparing positions across moving GLFW and parent coordinate frames consistently is an implementation implication (**I**), not permission to infer that every edge shares stored coordinates. The numerical correction in E55 is especially useful: a Melty left edge at 1900 cannot push a GLFW left edge at 340 while separated.

## Corrections that repeatedly mattered

- **Moving the outer opposite edge too early.** Active view edge-switching must not directly slide GLFW's opposite edge before physical contact. E52 states: “The active view being dragged is the ONLY view that switches edges.” E55 supplies numerical geometry contradicting the assistant's explanation.
- **Treating windows as indivisible rectangles.** Overlap is not a reason to skip collisions during GLFW shrink. Lukas gives the intended interleaved order `A.top → B.top → A.bottom → B.bottom`, rejecting collapse of all boundaries onto the GLFW bottom. [E65]
- **Over-broad nested special cases.** Skipping all parent/child or self-edge collisions loses correct behavior. The exception is specifically collision with the child's driving edge, and driving edge is not always top/left. [E71–E74, A4]
- **Testing only inner-to-outer interaction.** Native outer resize must also push contents; children carried by parent resize must participate. [E44, E45, E76]
- **Intercepting a column drag as native-window resize.** Column width must change while vertical drag continues to resize the enclosing window. [E100, E101]
- **Confusing a working moment with a durable result.** Multiple “works well” messages are followed by corrected failures, jitter, runaway speed or feedback. Particularly E105 is immediately qualified in E106; neither is a stable acceptance verdict.

## Ambiguities and limits

- **Minimum mechanics:** cascade intent is clear, but no recovered original user message defines a complete mathematical minimum solver, priority among simultaneous constraints, or behavior for contradictory min/max values. Treat such details as open, not recovered requirements.
- **Sticky scope:** latest request is broad, but exact unwind order, reversal after changing the chord, release/regrab semantics, and interactions with externally changed geometry are unspecified. August allowed a GLFW fallback if infeasible; September renews general support. Preserve that evolution.
- **All edges versus temporary rollback:** symmetric behavior is intended, but historical disabling is real. This document does not infer which features were enabled at any particular commit.
- **Packed GLFW shrink:** requested opposite-edge slide is clear; reverted fixes make it unsafe to infer a particular algorithm or that the requirement was withdrawn.
- **Move offscreen versus top clamp:** E57 (August 27) allows partial offscreen movement. A6 (August 28) then explicitly requests a hard top-of-display limit for Melty windows; E78 extends it to nested windows. The later top-specific correction narrows the earlier permission. It does not establish equivalent hard limits for left, right or bottom during a move.
- **Sibling interaction scope:** E58 limits inter-window collisions to GLFW resizing. Later generic language is not enough to silently expand this to every gesture.
- **Margins:** external left/right contact is explicitly zero. “Usual margin” for same-side/internal edges is not numerically defined. Display-edge drag should not leave a decorative margin gap [E35, E36], but September's separate Hyprland request includes a configurable left dock safe zone [E92]; that is not automatically a Melty requirement.
- **Native-child coordinate spaces:** “nested os window” in September 16 needs care; it cannot be merged with parent-relative in-app child positioning without additional evidence. No DPI, zoom, multi-monitor or coordinate-conversion formula was recovered.
- **Verification:** no implementation, test, live app, screenshot or video was inspected for this review. Original screenshot references therefore support textual complaints only. This is a requirements reconstruction, not an assertion that the current software meets it.
